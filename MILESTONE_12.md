## Objective and baseline

Complete the proposed twelve-chapter learning path with an integrated review of the existing Distributed Monitoring System V0: operational question, coherent definitions, controlled experiment, reproducible checks, qualified evidence and accountable next decision.

SITE_SPEC.md, DEMONSTRATOR_SPEC.md and MILESTONE_01.md remain authoritative. Build on Chapter 11 release `f13f700527da5af69b0fe7b0c2a7314549ec8246`. Preserve canonical YAML, stable IDs, pure calculation/evaluator, numerical contract/model version, assertions and reference/proposal record meanings.

“Integrated” means a connected learning and review path through existing sources and tools. It does not claim a new engineering platform, deployed operational system or implementation of demonstrator capabilities V1–V4. Completing the curriculum is distinct from delivering those future capabilities.

## Chapter contract

**Title:** The Integrated Engineering Environment.

**Question:** “Can another engineer follow this proposal from operational intent to a justified next decision?”

Target 800–1,200 words of main prose excluding exercise, source map and quiz. Start with a handover request: review a radius-only monitoring proposal and explain what its result establishes, which work actually ran and what remains unresolved.

1. Revisit the operational need before artifact IDs. Explain why the V0 geometric criterion is a teaching assumption and why passing it does not establish real-world monitoring effectiveness.
2. Connect existing intent, requirement, scenario, model, registered assertions, proposal analyses and execution context through their distinct roles. Use an inspectable source-linked route rather than a second definition set or general-purpose graph.
3. Guide one controlled radius-only proposal through definition comparison, validation, shared calculation and evaluation. Contrast the threshold example as a different requirement decision outside that assignment; do not combine candidates or introduce a new calculation.
4. Explain what each existing activity contributes: browser exploration, software assertions, reference evaluation generation, unapproved proposal analysis, review and publication. A published lesson is not an approved sensor design.
5. Ask the reader to inspect actual evaluated definitions and provenance, preserve canonical FAIL and distinguish successful software checks from requirement outcomes. Missing evidence must stay explicit.
6. Complete a short written handover: bounded claim, sources/revision, actual differences, actual execution/observations, assumptions, evidence gaps and responsible next review. No approval or operational acceptance is recorded.
7. End with an integrative reasoning quiz and a concrete conclusion about the engineering principle learned. Link back to relevant chapters for remediation and clearly label future capabilities as separate unimplemented work. Do not add a misleading next chapter placeholder.

Prefer repository facts and local teaching conventions. Verify any general standards, named-system or platform claims against authoritative primary sources during writing. Do not claim formal assurance, autonomous agents or production readiness.

## Capstone exercise

Provide a no-install browser route and a reproducible repository route. Reuse the existing ProposalWorkspace once, plus source links and native disclosures; no duplicated calculation, new input language or persistent handover form.

- State the operational question and inspect the canonical intent/criterion/geometry/method/assumptions.
- Try the radius fixture, inspect exact differences and proposed definitions, and write a bounded geometric claim under the unchanged criterion.
- Reset and inspect the threshold fixture. Explain the changed claim and assignment boundary despite a modeled PASS.
- Break/restore a reference and reset. Explain why invalid definitions block analysis while missing operational justification remains a separate review finding.
- Inspect an actual generated record or available CI artifact through existing instructions. Identify actual revision/dirty state and commands completed; do not imply the page has loaded historical evidence.
- Write the handover using a concise template. Reveal a clearly labeled reasoning guide after the reader attempts it. The guide must not fabricate an execution, named reviewer or approval; derive numeric examples through the shared workspace or omit fixed results from prose.

Repository instructions should reuse npm ci, npm run check, npm run evidence and npm run proposals, and inspect actual records. Do not require canonical edits, push, merge or publication to complete the exercise. Reference generation remains distinct from assertion execution; proposals do not claim TEST-COV-001 execution against changed inputs.
